# Resource footprint decision

## Measured trigger

The fresh 30.33-second native football-worker profile in `.desktop-runtime/playback-baseline-worker-2.cpuprofile` attributes about 4.18 sampled seconds inclusively to `sweep`, 4.09 to `reconcileProbeJobs`, and 3.51 to `persistWorkingIdentity`. These inclusive times overlap. The coordinator calls reconciliation twice per 15-second sweep. It visits every playable candidate and asks the store to replace each identity. The store parses the proposed feeds, serializes them, and queries existing payloads before it can return without a write. The fresh profile does not show a database write count. A copied-state replay must establish that these calls repeat unchanged identities before the implementation changes.

The copied `schedule-cost-clone.sqlite` contains 83 saved working feeds. With the coordinator clock fixed at `1791501590000`, six sweeps took 396.89 ms wall time and 438 ms process CPU. They made 168 `replaceWorkingIdentity` calls for 14 distinct identities. The ordered saved-row digest was `3022e78bce7709d6ee40634645c0c1a37a51c2fe232c11634cf7648d17a87586` before and after. The replay therefore confirms repeated unchanged persistence work. It does not claim the whole native process tree will fall by the same amount.

## Persistence sketches

**A. Coordinator dirty identities.** Keep a set keyed by `gameId` and probe identity. Mark it when a playable proof arrives, candidate aliases or source IDs change, a schedule changes owner or eligibility, or a candidate is removed. Reconcile only marked identities, and remove a mark after persistence succeeds. This removes coordinator alias construction and store validation for unchanged identities. It places invalidation responsibility beside the state transitions that know why the identity changed. It must preserve immediate proof removal and owner fencing. A missed mark risks stale persisted feeds after restart.

**B. Repository no-op payload cache.** The repository holds the last canonical payloads per identity and compares them before schema parsing and SQLite reads. It seeds the cache on store creation and updates or clears it after each write or removal. This keeps the coordinator's unconditional calls but makes unchanged calls cheaper. The coordinator still computes aliases, locators, and feed objects for every candidate. The store would also maintain a second representation of durable state, with invalidation on sweep and direct database changes in tests.

Choose A if the copied-state benchmark shows repeated identities with equal persisted rows, because it removes the measured work at its source. Choose B only if the replay shows the store validation and query dominate while coordinator computation is negligible. The benchmark must compare the same frozen SQLite fixture before and after, assert identical saved rows and public board and source results, and report wall and process CPU time. Neither choice changes media probe admission, its five-minute recheck, or today and tomorrow coverage.

The measured replay selects a narrow version of A. The 15-second sweep changes time-based eligibility and prunes stale candidates, but it does not create a new playable proof, alias, or source listing. Probe completion persists its own proof, and schedule, detail, and catalog publication still reconcile and persist changed identities. Skip identity persistence only in the sweep's two reconciliation calls. Continue all of their cancellation, expiry, and proof-removal work. This avoids a second persistent cache and limits the change to the measured no-op path. Verify the saved rows and public snapshots on the same copied fixture and retain the existing tests for alias updates, final transitions, and restart recovery.

## Sources panel trigger

`app/page.tsx` mounts every Settings tab with `forceMount` while the Settings dialog is open, including Sources when another section is selected. `SourceInventory` immediately fetches `/api/sources` and polls every 3 or 15 seconds while mounted. The parent already renders Settings conditionally, so closing the dialog unmounts the inventory even before this change. The page also runs its own source polling for player choices. Make the Settings tab controlled by page state and mount `SourceInventory` only when Sources is selected. Keep the selected Settings tab across close and reopen. A browser regression should show no inventory instance or extra source polling on General, exactly one inventory instance on Sources, and normal polling after returning to Sources. The room's player and board state must persist through opening and closing Settings. The native root renderer's roughly 13,000 nodes were observed with Settings closed, so this panel change does not explain that count.

## Verification and limits

`tests/benchmark-working-feed-sweep.mjs` replays six sweeps in each mode against a fresh copy of the same frozen SQLite database, alternates mode order for five pairs, and asserts equal saved rows, board, and source snapshot hashes. The final run measured 168 versus zero `replaceWorkingIdentity` calls. Both modes had 83 saved rows, with identical saved-row digest `3022e78bce7709d6ee40634645c0c1a37a51c2fe232c11634cf7648d17a87586`, board digest `36f86a28525bdcf3b5d100ee652dad22d6c754a5fbb226adbfa9d66356e41a6a`, and sources digest `8e11910798b4337c16649297916fbd9de2b4a83f58160d95c9850d7fae64769d`. The median wall measurements were 244.92 versus 274.39 ms and median process CPU was 250 versus 250 ms. This short replay proves the repeated work was removed and public results held constant; it does not establish a stable CPU or wall-time reduction, nor a native-process improvement. A previous five-pair run gave 347.29 versus 300.49 ms wall and 329 versus 266 ms CPU, showing the timing variation. The final raw samples are in `.desktop-runtime/resource-footprint-benchmark.json` in the worktree.

Reproduce from the worktree with `node --experimental-strip-types tests/benchmark-working-feed-sweep.mjs ../schedule-cost-clone.sqlite 1791501590000 5`; the script copies the fixture into temporary databases and leaves the frozen input unchanged.

`tests/settings-sources-mount.browser.mjs` drives an isolated webpack Next development server. It verifies that the inventory is absent before Sources opens, polls twice while visible, stops polling on General, remounts once on Sources, and retains the room layout and selected Settings tab. It also checks polling stops after Settings closes, which was already true before the change. The inventory's own search and league filters reset on remount; they are transient view controls, while the room preferences and selected Settings section remain in page state. The conditional client render follows this repository's installed Next 16.3.4 `use-client` and server/client boundary guides in `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-client.md` and `node_modules/next/dist/docs/01-app/02-guides/server-and-client-boundary.md`.
